# 工程预设体系:两档预设,分层为主、条件为辅

jfast MVP 恰好提供两档工程预设:`empty`(空工程)与 `full`(完整后台),第三档(如纯后端 API 版)进路线图。空工程与完整后台**同栈同结构**——前后端骨架、构建/配置/CI、数据库配置全在,只缺系统管理功能包——因此两档共享同一份基础骨架,差异只靠两种机制表达:**分层为主**(整个文件属于某预设 → 放预设 overlay 目录,`templates/base/` + `templates/presets/<name>/` 纯叠加,同路径撞车报错,不可覆盖/删除 base 文件),**条件为辅**(共享文件内的小段分叉 → Freemarker `<#if conditions.*>`,MVP 仅布尔变量)。预设由目录扫描自动发现,每档预设带一个 `preset.yaml` manifest(name / displayName / description / questions / conditions 五字段,未知字段报错),加预设零改代码;`empty` 也有 `presets/empty/` 目录,仅放 manifest 不放模板,保持所有预设形态统一。核心论证:① 分层与条件分工的判据(整文件归预设 vs 文件内分叉)直接来自原型(#5)两个结论的合流——「目录分层直观」+「条件文件需元数据约定」,manifest 的 `conditions` 字段就是该元数据约定的落地;② 纯叠加禁止覆盖/删除,把结构冲突暴露在生成期而非静默覆盖,心智成本最低;③ manifest 白名单 `questions` 让向导问题树按预设装配,新问题默认对所有预设不可见,比黑名单保守;④ 扫描发现 + 统一形态是将来第三方预设生态(地图迷雾项)的接口雏形,`--preset-path` 外部目录留参数位但 MVP 不实现。

## Considered Options

- **条件为主(一套全量模板,empty = 一堆条件关闭)**:模板内条件爆炸、可读性差,文件级差异用条件表达会把「有没有这个文件」藏进渲染逻辑。拒绝,仅保留为文件内小分叉的补充机制。
- **代码注册预设(新预设改 Java 代码)**:预设清单硬编码,加预设要动生成器本体,与「目录即模板」的目录驱动哲学相悖。拒绝。
- **base 裸用(empty 无 `presets/empty/` 目录)**:empty 变成特例,目录扫描、manifest 查找、向导展示都要写分支。拒绝,统一形态的成本只是一个几乎空的目录。
- **overlay 可覆盖/删除 base 文件**:覆盖语义让「最终产物长什么样」要脑内合并两层才能回答;删除标记更增一类元数据。拒绝,base 里不得放「某预设需要不同版本」的文件——这类文件改为条件渲染或移入 overlay。
- **参数模式 `--preset` 给默认值**:预设选错代价大(空工程没法补、完整后台删代码烦),非 TTY 场景已强制全参数模式,显式书写对 CI 脚本更友好。拒绝,`--preset` 必填、缺省报错并提示可选值;向导内同样必选、无默认选中项。
- **`questions` 用黑名单(列出不问的)**:新加问题时默认对所有预设可见,empty 容易被功能问题污染。拒绝,用白名单。
- **条件变量允许枚举/字符串**:两档预设的差异就是「有无」,枚举是过度设计。MVP 拒绝,仅布尔。

## Consequences

- **CLI 呈现**:向导中预设是 Tab 表单必选单选项(无默认);参数模式 `--preset empty|full` 必填。问题树裁剪由 manifest 的 `questions` 白名单驱动:empty 只问工程元数据(groupId / artifactId / 包名 / JDK 等),full 问全量;编排层按预设装配问题集,不在问题里写 if。
- **条件渲染语法**:统一 `conditions.*` 命名空间,一眼可辨是预设条件而非普通模板变量;用 Freemarker 默认尖括号语法(与 `.vue`/TS 泛型不冲突),若日后发现冲突再切 `[@#if]` 方括号语法。
- **质量门禁**:生成器仓库 CI 对每档预设跑「生成 → 后端 `mvn compile` → 前端 `npm run build`」,全绿才合入;更广的测试矩阵(快照测试、生成物矩阵)归「生成器自身的测试策略」迷雾票据。
- **路线图**:纯后端 API 预设(无前端)记入地图迷雾,不在 MVP;第三方预设生态维持迷雾项。
- 与 ADR「MVP 功能清单」(#9,完整后台固定全量打包)与 ADR-0003(#10,空工程条件渲染分叉)一致:预设之间不做功能选配,档内全量、档间分层。
